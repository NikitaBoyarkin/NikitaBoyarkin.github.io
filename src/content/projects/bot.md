# Reporting Automation Telegram Bot

## Задача

Каждую неделю аналитик вручную собирал метрики из нескольких источников, обновлял дашборд, экспортировал скриншоты и рассылал их в рабочий чат. Процесс занимал 1–2 часа, часто задерживался и зависел от одного человека. Задача — перенести сборку отчёта в бота, который сам запрашивает данные и отправляет их по расписанию: команда получает метрики регулярно и в одном формате.

## Данные и метод

**Данные:** продуктовые метрики из базы данных (SQL), внешние API и готовые дашборды Tableau.

**Архитектура бота:**

1. **Планировщик** — запуск по cron в заданное время.
2. **Сбор данных** — SQL-запросы к витрине данных, агрегация ключевых KPI (DAU, ARPU, конверсия, retention).
3. **Формирование отчёта** — шаблон с KPI-таблицей, sparklines и сравнением с прошлой неделей (дельта в % и pp).
4. **Отправка** — Telegram Bot API в указанный чат или по команде `/report`.
5. **Надёжность** — обработка ошибок, логирование, fallback-уведомления при сбоях источников.

**Инструменты:** Python (aiogram/telegram-bot), SQL, cron, Tableau для визуализации.

## Результат

Ручная сборка отчёта оказалась не столько сложной, сколько фрагментированной: метрики приходилось дёргать из разных мест. После консолидации в одном пайплайне большая часть работы перешла на машину — ручные 1–2 часа заменил cron, а аналитик стал отвечать за интерпретацию, а не за копирование цифр.

## Ограничения

Стабильность доставки здесь важнее красоты отчёта: если бот падает silently, доверие к метрикам падает быстрее, чем растёт экономия от экономии времени. Поэтому fallback-уведомления при сбое источника встроены в архитектуру, а не добавлены «потом». Репозиторий приватный — публичного кода нет, карточка не ведёт на пустой репозиторий.

## Документация

- Репозиторий приватный — доступ по запросу. Публичного кода нет; карточка не ведёт на пустой/stub-репозиторий.
