## 1. Почему v9, а не продолжение v8

`prd-v8.md` поставил сайт за гейт аутрича и был прав в диагнозе: узкое место — не вёрстка.
Гейт отложен (`docs/backlog.md` B-1), P0-Content пошёл без него. За три недели после v8
сайт получил новый слой: роль-лендинги, градиентную семью, четыре новых кейса.

И тут обнаружилось то, чего не видел ни v7, ни v8. **Пайплайн, который выкладывает сайт
в прод, — красный.** Последний пуш (`4274406`, «Add new projects: ML Fundamentals, SERP
Rank Lab, Airflow DAG Platform, LinkedIn Content Analytics») не доехал: гейт `make check`
упал на четырёх тестах, job `deploy` не запустился, живой сайт остался на сборке
от 15:24Z того же дня — без этих четырёх кейсов.

v8 защищал от «полируем актив, которого никто не видел». v9 фиксирует, что актив может
**не доехать до читателя вообще** — и ни один существующий механизм об этом не сообщает.

**Что v9 добавляет к v8:**

| Добавление | Зачем |
|---|---|
| Публикация как P0, а не как фон | Красный деплой обнуляет любую работу над контентом |
| Сигнал о падении деплоя | Механизм есть, наблюдателя нет — падение неотличимо от тишины |
| Закрытие молчаливого `skipped` в Lighthouse | Вторая половина проверок исчезает без сообщения |
| Разделение «сделано агентом» / «опубликовано» | Локально зелёный `make check` ≠ сайт обновился |

## 3. Корневая причина: механизм без сигнала

`deploy.yml` устроен правильно. Единственный гейт — шаг `Validate built site`,
он же `make check` (`deploy.yml:130-136`); job `deploy` зависит от `build` через
`needs` (`deploy.yml:146`) и не запускается, если сборка упала. Гейт сработал ровно так,
как задумано: четыре красных теста остановили публикацию.

Проблема не в гейте, а в том, что **у падения нет наблюдателя**:

| Что есть | Чего нет |
|---|---|
| `make check` падает с exit 2 | Ни одного уведомления — ни в GitHub, ни наружу |
| `lighthouse.yml` на `workflow_run` | При падении деплоя он **молча скипается** (`38180509168`) — perf/a11y перестают проверяться без сообщения |
| Локальный `make check` — та же команда | Ничто не связывает «локально зелёно» с «опубликовано» |

Это ровно тот случай, который описывает `.claude/rules/claim-mechanism.md`:
механизм без наблюдателя неотличим от отсутствия механизма. Гейт — сильнейший класс
проверки, но только если кто-то видит его красным.

**Следствие.** Четыре новых кейса пролежали бы в `master` неопубликованными до
следующего пуша — а следующий пуш, скорее всего, был бы правкой чего-то другого.

## 6. Метрики

**North Star v8 не меняется:** контакты в месяц. v9 добавляет метрику, которая стоит
**до** неё по каузальному пути — без неё North Star недостижим по определению.

| Метрика | Где | Хорошо | Плохо |
|---|---|---|---|
| Deploy-green streak | GitHub Actions | ≥ 10 пушей подряд | 2+ подряд красных |
| Time-to-detect (падение → узнали) | `gh run list` | < 1 часа | > 24 часов |
| Доля пушей, доехавших до прода | Actions | 100% | < 100% |

Пороги для первых двух — не «мягкие»: они проверяются командой, а не суждением.

## 8. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Пуш не сделан, сайт остаётся старой сборкой | **Высокая** — это состояние по умолчанию прямо сейчас | G1 — единственная задача, блокирующая всё; без неё PRD не имеет смысла |
| Следующий батч контента снова уедет красным | Средняя | G2 закрывает обнаружение; G5 — понимание |
| Уведомления (G2) начнут шуметь на каждый красный PR | Средняя | Уведомлять только о падении на `master`, не на PR |
| Локальный `sync:gh` без токена бесполезен для проверки | Средняя | Задокументировать `GITHUB_TOKEN` как обязательный для локального прогона |
| Четыре кейса пролежали зелёными локально и красными в CI | Уже случилось | Причина — контент, а не инфраструктура; локальный `make check` их ловит, если запускать его до пуша |
